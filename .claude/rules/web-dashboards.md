# Web dashboards

- Our widgets (and other apps', below) in any browser on the home network, on dashboards laid out on the page itself (the user's choice over reusing Homey dashboards; home network only; a personal API key per browser). `settings/dashboard.html` (+ `dashboard.js` and its parts, `dashboard.css`, `socket.io.js`), served by the Homey without login at `http://<ip>/app/<appId>/settings/dashboard.html`. The app settings page shows the address (`GET /web/address`, `homey.cloud.getLocalAddress()`). It loads the kit as `../widgets/spacer/kit.js` (and `.css`), the Homey's path, not the repo's `public/` one (a 404 on the Homey, which left `WidgetkeeperKit` undefined and the value slots empty, 2026-10-18); the dev pages load their own. `lib/WebDashboardService.ts` keeps the dashboards.
- **The page's script** (split 2026-10-30, the user's ask: one 4,250-line file): `settings/dashboard.js` is the core (the strings, constants and helpers, `keepAwake`/`applyDim`, then `mountWebDashboards()`: the page's state, the app's API (`request()`, `homeyRequest()`, `loadAll()`), saving (`persist()`, `failed()`, `toast()`) and routing (`route()`, `start()`)). The rest is in parts, `settings/dashboard-<part>.js`, loaded after it in `PARTS`' order (`dashboard.html` and the two dev pages list them): `realtime` (the socket), `frames` (the crossframe protocol, `handle()`, frame heights, themes), `views` (the chrome, key and password screens, a dashboard, its bars, `syncGrid()`), `front` (the front page, its sections, Settings and the backup), `editing` (wide widgets, moves, drag and drop, resizing), `settings` (Add widget, `editWidget()`, the live preview, the setting controls), `pickers` (devices, values, autocompletes), `popups`, `sync` (syncing with Homey dashboards, `.claude/rules/web-sync.md`) and `screen` (Dim at set times and from a Flow, Rotate dashboards), `icons` (the header's name and icon, a dashboard's icon) and `nav` (the side pane). Each registers `WidgetkeeperWeb.part(name, (wd) => …)`; `mountWebDashboards()` runs them in order with `wd`, the page's shared object: the core's functions and constants are destructured from it at a part's top (so they read as before); **the state that changes is only ever `wd.<name>`** (`wd.current`, `wd.setup`, `wd.key`, `wd.dashboards`, `wd.drag`, `wd.saving` …), as is another part's function (`wd.syncGrid()`); a constant only one part uses lives in that part. A missing part throws `settings/dashboard-<name>.js isn't loaded`. The split was mechanical (Babel's scope analysis, every cross-file reference rewritten) and checked in headless Chrome against the unsplit page: every web-showcase view and 30 states of `dev/web-preview.html` (dialogs, pickers, moves, drag and drop, resizing, arranging cards) gave the same DOM. The tests read the page's helpers from all its files (`webPageSource()`, `test/helpers/webPage.ts`).
- Each widget runs **unchanged** in an iframe of its own `../widgets/<id>/index.html?widgetInstanceId=web-<dashboardId>-<widgetId>`: the Homey injects its SDK (`/js/crossframe.js`, `/widgets/js/homey.widgets.js`) and stylesheet (`/widgets/css/homey.widgets.css`, which the page loads too: Homey's real tokens, fonts and `.homey-dark-mode`) into every served widget `index.html`. Outside a WebView the SDK's crossframe posts to `window.parent`, so the page answers it as Homey's dashboard does: `getInitialData` (`{settings, deviceIds, transparent, locales, language, devmode, fontScale, isDarkMode}`), `api` (→ `POST /web/call {type, method, path, query, body}` → the widget's own `api.ts`, `callWidgetRoute()`), `registerRealtimeListener` (data is the event name; every event is a `cb` with `args: [data]` and that callbackId), `ready`/`setHeight` (the iframe's height, `setFrameHeight()`: Homey's docs allow a number, a string or null; a number or numeric string is px, `'50%'` an aspect ratio as in a manifest, anything else is ignored, where `Number(null)` made it 0 px before 1.1.0; the SDK, `/widgets/js/homey.widgets.js` read from the Homey 2026-10-24, sends both as `{height}`), `popup`, `shortPressHapticFeedback`, `emit`. Messages are `CF2_MESSAGE` + UTF-16 hex JSON (`hexEncode()` through a byte table); an error is `{type: 'Error', data: message}`. The iframes are `loading="lazy"`.
- A widget of ours that `popup()`s `#/d/<id>` (on the page's own path, or the frame's) opens that dashboard in place (`dashboardLink()`), not from the editor; any other URL opens a window. Dashboard Shortcuts (`.claude/rules/widgets/shortcuts.md`), a widget only the web dashboards offer (deprecated in its manifest, so Homey's own Add widget leaves it out), is what uses it.
- Requests: `fetch('/api/app/<appId>/…', {Authorization: 'Bearer <key>'})`, same origin (a personal API key may call the app's API, 2026-10-10). The key is `localStorage` `widgetkeeper.web.key`; a 401/403 forgets it, stops the socket and brings the key screen back. The app's own token still does everything else. A route that acts with the stored key (`routeKeyUse()`: variables `/set`, flows `/trigger`, media `/button` (a `card:` needs `homey.flow`), stack `/pages`, lights `/mood`, and a stack `/call` of those) only runs when the page's own key may do the same: `/web/call` carries `key`, and `PersonalApiKey.scopesOf()` reads its scopes (remembered 60 s; a passing failure throws and isn't kept). `/web/autocomplete` carries it too, for the Smart Stack's dashboards (`autocompleteKeyUse()`); else `{ok: false, reason: keyScope | keyInvalid}`, so a weaker key can't borrow the stored one's permissions. Likewise a device change with the app's own token (`DEVICE_WRITES` in `lib/widgetRoutes.ts`: quickactions `/trigger`, lights, lightrooms and curtains `/set`, locks `/set` and `/open`, thermostat `/apply`, media `/set`; `pageKeyUse()`, which `/web/call` uses, adds them to `routeKeyUse()`'s) needs the page's key to control devices (`devices`: `homey.device.control`, `homey.device` or `homey`), else it throws `This browser's API key may not change devices (keyScope)` and the widget shows its own failure (the security audit, 2026-10-24: an *Apps → Control* key reached the app's routes and could have unlocked any lock). A test makes every non-GET widget route either a stored-key use, a device write or one it names as neither. Reads stay the app's: a key that may open the page sees what the widgets show. On `http:` (the home address) the key screen also says the address isn't encrypted (`web.keyPlain`; the security audit, 2026-10-24): the key goes in the clear with every request and the socket's handshake, and the README (*Web dashboards' key*, *Away from home*) says to use the away address on a network you don't fully trust, and a key per browser. Homey's `https://<ip-with-dashes>.homey.homeylocal.com` (below) would be encrypted at home if a local DNS entry resolved it; not tried in a browser, so not in the README.
- Realtime without homey-api: socket.io v2 to the Homey (`transports: ['websocket']`), `emit('handshakeClient', {token, homeyId}, cb)` → `{namespace: '/api'}`, `io.socket(namespace)` and `.open()`, `emit('subscribe', 'homey:app:<appId>', cb)`, then events arrive as `ns.on('homey:app:<appId>', (event, data))` (2026-10-10). `homeyId` comes from `/web/setup` (`homey.cloud.getHomeyId()`). Any failure or disconnect starts over (2 s, doubling to 60 s); after an outage over 30 s the frames reload. `No live updates` shows while it's down.
- Endpoints (`api.ts`): `GET /web/setup` (`{appId, homeyId, language, strings, widgets: widgetTypes(), dashboards, front, maxDashboards, maxWidgets, maxSections, popups}`), `GET /web/devices?type=&query=` (the manifest's `devices.filter`: `class`/`capabilities` as `a|b`, the class or the virtual class; `{id, name, zone: {id, name, path} | null, icon}`, the icon the same-origin `/api/icon/<id>` (no login needed) or the library URL), `GET /web/values?type=`, `POST /web/autocomplete {type, setting, query, settings}`, `PUT /web/dashboards` (a new one gets an id), `PUT /web/front` (the front page's order and carousel), `DELETE /web/dashboards/:id`, `POST /web/dashboards/:id/copy` (Duplicate), `POST /web/dashboards/:id/widgets/:widget/copy` (Copy to…), `GET/PUT /web/backup` (the front page's backup), `POST /web/call`, `GET /web/address`, the password routes and the screens' (below).
- On/off: the app setting `webDashboardsEnabled` (off unless `true`), a checkbox on the settings page, which shows the address only while it's on. Off, `/web/setup` answers only `{disabled: true, language, strings}` (`web.off`) and every other `/web/…` route but `/web/address` throws `Web dashboards are turned off` (`assertEnabled()`); the dashboards stay. The page's `failed()` goes back to `start()` on that error.
